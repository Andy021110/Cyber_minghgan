## 一、已对齐的部分

### 1.1 产品定位

**当前阶段定位：可视化认知记忆镜子（Memory Mirror）**

- 核心价值：持续记录、整理你的行为模式，让你更了解自己，并在决策前给出基于历史模式的个性化建议
- 不是通用 AI 助手，是有你这个人的具体人格记忆的对话体
- 三层心理结构（Id / Ego / Superego）是真正的差异化护城河，不是装饰

**与竞品的本质区别：**

| 产品 | 路线 | 缺陷 |
|------|------|------|
| Replika / Character.AI | 黑盒微调大模型 + 3D 虚拟人 | 记忆逻辑不可审计，3D 成本高 |
| Obsidian / Roam | 纯文本知识图谱 | 枯燥，没有"活物"感 |
| 赛博明翰 | 可审计 KG（严谨）+ 像素空间交互（情绪价值） | — |

---

### 1.2 核心交互范式

**空间交互替代命令行**

- 走到咖啡机 → 触发健康教练，点击白板 → 触发工作规划
- 后台完全静默，用户感知的是「在过日子」而不是「在调用函数」
- 星露谷美学的深层逻辑：游戏的「有限时间下资源分配」与心理三层的「有限意志力下冲突仲裁」同构

**三层的空间映射（建议）：**

| 心理层 | 空间对应 | 视觉感 |
|--------|----------|--------|
| Id（本能欲望） | 矿洞 | 黑暗、冲动、即时收益 |
| Ego（现实协商） | 农场 | 日常管理、现实约束 |
| Superego（道德规范） | 小镇 | 社区规范、关系压力 |

**移动端碎片化场景（已解决）：**  
架构 API 优先，保留极简文字接口（快捷指令 / 微信 Webhook），允许绕过 RPG 界面直接写入 pending.jsonl。

---

### 1.3 架构原则

**前后端彻底分离 + 本地存储主权**

- Python 后端处理所有核心逻辑，前端通过 API 调用
- 数据文件（KG / 队列 / 日志）锁在本地，不上传第三方存储服务

**数据主权的准确表述（重要修正）：**

当前实际状态是「**本地存储 + 云端推理**」，不是完整的本地主权：
- 每次 API 调用，KG 节点内容、对话历史都会经过 Anthropic 服务器处理
- 真正的本地主权需要本地 LLM（Ollama + Llama / Qwen），代价是推理质量下降
- **当前阶段定位**：本地存储 + 可迁移，等产品验证后再评估本地模型替换

**并发写入（已识别风险）：**

多端并发时 `.jsonl` 文件存在写入冲突风险。解决方案二选一：
- 轻量：API 层加请求队列，所有写操作串行
- 健壮：迁移至 SQLite（长期推荐）

---

### 1.4 外部数据接入

**Webhook + 统一清洗层**

- 不逆向破解微信 / 苹果沙盒，只用官方允许的 Webhook 和 Shortcuts
- 所有外部数据（微信、Apple Health、快捷指令）经统一清洗层格式化后再进蓄水池

**清洗层标准格式：**
```
在 [时间]，通过 [渠道]，发生了 [事件]
```

---

### 1.5 记忆镜子 vs. 数字分身

**当前阶段：记忆镜子（已确认）**

- 回答「我是什么样的人」「我过去有什么模式」
- 支持「决策前建议」：给定即将发生的场景，AI 检索相关节点，给出个性化建议
- 该需求**不需要分身架构**，在现有镜子基础上加一个面向未来场景的提问入口即可

**数字分身（v2，待议）：**

- 回答「我接下来会怎样」
- 需要节点间有向边（因果权重），以及模拟推理引擎
- 见第二章「待议事项」

---

### 1.6 冷启动设计

**当前用户（你 + 少数朋友）：冷启动问题不存在**

已有 133 条活跃节点，系统已具备足够上下文。

**未来陌生用户场景：**

- 不用 MBTI 类型题（测稳定特质，颗粒度不匹配）
- 用 CBT 初始评估风格的行为问卷，直接产出 Id/Ego/Superego 种子节点
- 问题示例：
  - 「最近一次你放弃了一个计划，当时发生了什么？」
  - 「你通常用什么方式应对你不想做但必须做的事？」
  - 「你最常在什么时候对自己感到失望？」
- 目标：30 分钟问卷替代前 10 次自然对话的冷启动期

### 1.7 UI 形态与技术选型

**已对齐：Web 应用（本地服务）**

| 维度 | 决策 | 理由 |
|------|------|------|
| 形态 | 本地 Web 应用（浏览器打开） | 像素风渲染最成熟，布局自由度高 |
| 后端 | FastAPI（Python） | 直接复用现有 `CyberBrainStore` 和 pipeline 代码，不需要重写业务逻辑 |
| 前端 | HTML + CSS + 轻量 JS（无大型框架） | 像素风 UI 更适合纯 CSS + Canvas，React 反而增加复杂度 |
| AI 对话接入 | 方案 A 先行（改 I/O 层，不动核心逻辑） | 快速落地；功能稳定后再考虑方案 B（brain_core 拆分） |

**分阶段路径：**

- **P0（当前优先）**：可视化展示层 + 静态设计稿 — 像素风场景 HTML 原型，无后端交互
- **P1**：接入 FastAPI，/kg 和 /review 功能迁移到 Web UI
- **P2**：AI 对话框接入，streaming 显示，反刍引擎确认框
- **P3**：像素角色动画，场景切换动效

**开放问题（待议）**：
- 像素场景是 Canvas 绘制还是 CSS Sprite？后者更易于设计师出图，前者动画更流畅

### 1.8 视觉风格基准

**已对齐：「星露谷 × 精神分析」暗色像素风**

**色彩系统：**

| 用途 | 颜色值 | 说明 |
|------|--------|------|
| 背景基色 | `#0d1117` | GitHub 暗色，已在力导向图中使用，延续 |
| Id 层（本能） | `#e05c5c` | 红色 — 冲动、欲望、危险感 |
| Ego 层（现实） | `#3fb950` | 绿色 — 成长、稳定、现实感 |
| Superego 层（道德） | `#f0a500` | 橙色 — 警示、规则、内疚感 |
| 文本主色 | `#c9d1d9` | 低对比度白，护眼 |
| 卡片背景 | `#161b22` | 比基色略亮，用于卡片/面板 |
| 边框 / 分割线 | `#30363d` | 低调边框 |

**像素风规范：**

- 字体：像素字体（如 `Press Start 2P` 用于标题）+ 系统等宽字体（内容区可读性优先）
- 图标：16×16 或 32×32 像素图标，不使用矢量图标库
- 圆角：0px（像素风无圆角）或只允许 2px 极小圆角
- 阴影：禁用 box-shadow，改用像素化 `drop-shadow`（偏移 2-4px，无模糊）
- 动画：帧动画（8fps）而非贝塞尔曲线缓动

**三层空间视觉映射（建议设计师参考）：**

| 层 / 空间 | 环境色调 | 光线感 | 氛围词 |
|-----------|----------|--------|--------|
| Id / 矿洞 | 暖红、暗紫 | 火把光，局部照明 | 冲动、黑暗、地下 |
| Ego / 农场 | 草绿、土黄 | 白天自然光 | 忙碌、现实、温暖 |
| Superego / 小镇 | 冷蓝、石灰白 | 黄昏或晨光 | 规矩、压力、庄重 |

## 二、待议事项

### 2.1 模拟推理引擎（数字分身核心能力）

**功能描述：**  
给定一个未来场景，遍历 KG 节点因果图，输出预测 + 建议。  
与镜子「决策前建议」的区别：基于节点间因果权重（精确），而非 AI 语义推断（灵活）。

**架构改动评估：**

| 组件 | 改动 | 难度 |
|------|------|------|
| KG JSON schema | 加 `edges` 数组 | 小 |
| CyberBrainStore | 加边的增删改查 | 中 |
| `/review` 流程 | 审批节点时标注关系 | 中 |
| 模拟推理引擎 | 全新组件 | 大 |
| 现有 133 个节点补边 | AI 从 evidence 推断，需 HITL | 中，但费时 |

**模块化承诺：**  
后端保持模块化设计，模拟推理引擎作为独立模块挂载，加入时不影响现有脚本运行。  
具体实现：推理引擎以独立文件存在（如 `pipelines/simulation_engine.py`），通过 `CyberBrainStore` 的只读接口读取节点和边，不修改现有写路径。

**触发条件（建议）：** 边的数量积累到 50 条以上再启动，否则预测价值有限。

**决策状态：⏸ 待议，优先级低于 UI 建设**

---

### 2.2 HITL 审批规模问题

接入 Webhook 后，蓄水池可能每天涨 20-30 条。当前「全量人工逐条审批」在规模化后会成为卡口。

**建议方案：**  
在 `batch_processor` 分类后加置信度分级：
- 高置信度 LOG 路由（饮食记录等）→ 可批量自动归档，免逐条审批
- 低置信度或首次出现模式 → 保持人工审批

**决策状态：⏸ 待议，当前数据量不构成问题**

---

### 2.3 像素场景渲染方案

**问题**：像素场景（农场 / 矿洞 / 小镇）用 Canvas 绘制还是 CSS Sprite 拼贴？

| 方案 | 优点 | 缺点 |
|------|------|------|
| Canvas 绘制 | 动画流畅，交互精准（点击区域精确） | 设计师出图格式需额外约定，前端实现成本高 |
| CSS Sprite 拼贴 | 设计师直接切图，前端拼接，改动容易 | 动画复杂度高，层级管理繁琐 |
| SVG（矢量像素风） | 缩放无损，代码可编辑 | 像素风手感不够，设计师工具链复杂 |

**建议**：P0 阶段用 CSS Sprite（设计师友好），P2 阶段视动画需求决定是否迁移 Canvas。

**决策状态：⏸ 待议，依赖设计师工具链偏好**

---

### 2.4 前端技术栈最终确认

当前对齐是「HTML + CSS + 轻量 JS」，但实际实现时需要确认：
- 是否引入 Vite 构建（像素风图片资源多，打包优化有益）？
- 状态管理用原生 JS 还是 Alpine.js / Petite-Vue（两者都轻量）？
- 字体加载：`Press Start 2P` 约 100KB，是否本地托管？

**决策状态：⏸ 待议，待 P0 HTML 原型验证后确认**

## 三、架构模块化原则（备忘）

为保证后续扩展不影响现有脚本，约定以下原则：

1. **新功能 = 新文件**：模拟推理引擎、Webhook 清洗层等均独立成文件，不修改现有 pipeline 脚本
2. **写路径唯一**：所有 KG 写操作经过 `CyberBrainStore`，新模块只调用其接口，不直接操作 JSON
3. **新组件只读现有数据**：推理引擎通过 `CyberBrainStore` 只读接口读节点，通过独立的边存储读边，两套数据互不污染
4. **边与节点物理分离**（如果未来加边）：边数组可存在 KG JSON 的独立 key 里，或单独一个 `kg_edges.json`，节点列表结构不变
