## 一、背景与目标

赛博明翰后端已完成：128 条 KG 节点、完整 HITL 审批流、8 个自动化测试通过。  
当前缺口是**前端为零**，需要从头建设一个「星露谷式像素 RPG 外壳 + 功能面板」的 Web 应用。

前端需要交付三件事：

1. **像素游戏世界**：玩家在像素房间里行走，靠近 NPC / 物件触发功能
2. **功能面板**：对话框、/kg 图谱浏览、/review 审批、/prune 老化管理
3. **前后端接通**：以上 UI 行为与现有 FastAPI 后端（或直接调用 CyberBrainStore）完全联动

---

## 二、为什么需要 4 个 Agent

前端工作天然分成三条**并行轨道**，每条轨道的技能要求不同，无法由一人高质量完成：

| 轨道 | 内容 | 所需技能 |
|------|------|---------|
| A — 视觉资产 | 像素角色、场景图块、UI 设计稿 | 像素美术 + UI 设计 |
| B — 游戏层 | Phaser.js 场景、角色行走、NPC 交互 | 游戏前端开发 |
| C — 面板层 | HTML/CSS 功能面板、API 对接 | Web 前端开发 + 后端接口 |

三条轨道都依赖一个前置条件：**有人先把接口和规范定好**，否则三条轨道各自乱跑，最终无法拼合。

因此拆成 **1 个架构 Agent + 3 个执行 Agent**，共 4 个 Agent。

## 六、为什么这套链路可行

**依据 1：后端已稳定，前端是纯交付问题**  
`CyberBrainStore`、`decision_log`、`batch_processor` 接口已经稳定且有测试覆盖。Agent 4 的工作是"包装"而非"重建"，风险低。

**依据 2：Phaser.js + HTML/CSS 双层是业界验证方案**  
这是 Web 游戏接 Rich UI 的标准架构，Phaser 官方文档有 React/Vue 集成示例，EventBus 模式有大量开源参考。技术路线没有未知风险。

**依据 3：三条轨道可并行，不互相等待**  
Agent 2 出图和 Agent 4 封装 FastAPI 可以同时进行，两者不互相依赖。Agent 3 可以先用占位资产开发场景逻辑，等 Agent 2 交付真实资产后替换。

**依据 4：Agent 1 的规范文档是最高杠杆动作**  
架构师花 1 周写清楚接口契约和资产规范，可以让后续三个 Agent 减少 80% 的返工沟通成本。这是最不能省的一步。

**依据 5：与 Stage1 游戏同源**  
赛博明翰的像素动画需求（角色行走、NPC 待机、交互动作）和 Stage1 的帧动画是同一套逻辑，只是工具从 pygame 换成了 Phaser.js。概念验证已经存在于你自己的代码里。
