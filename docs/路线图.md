## 1. 定位

**可信的个人代理——深度在记忆治理，不在工具数量。**

三个"不做"构成差异化：不做微信个人号自动回复（合规）｜不冒充本人欺骗面试官（诚信）｜不堆通用工具生态（不跟 Hermes 比数量）。

## 6. 回溯与实验机制（自主探索的地基）

以 Agent loop / harness 形式探索时，绝大多数决策不是"对或错"，
而是"合不合理"——只能靠实验定。没有回溯机制，探索会原地打转：
三天后只记得当前值是 λ=0.4，却忘了试过 0.6、结果如何、为什么退回。

三个层次，各管一段：

| 层 | 载体 | 管什么 |
|---|---|---|
| 代码回溯 | git + tag（如 `a0-persistence-safety`）+ 原子写 `.bak` | 回到某个能跑的版本 |
| 决策回溯 | `docs/关键决策记录.md`（ADR-001～011） | 当初为什么这么定 |
| 实验回溯 | `experiments/ledger.jsonl` + `evals/badcases/` | 试过什么、结论是什么、失败样本有没有复发 |

### 6.1 三件套

| 工具 | 回答什么 | 命令 |
|---|---|---|
| `experiments/ledger.py` | 这个决策凭什么这么定 | `python3 -m experiments.ledger` |
| `evals/replay.py` | 已修的缺陷有没有复发 | `python3 -m evals.replay` |
| `evals/health.py` | 这套工作流本身高不高效 | `python3 -m evals.health` |

判定语义：`fixed+fail → REGRESSION`（退出码 1，CI 阻断）／
`open+fail → OPEN`／`open+pass → RECHECK`／`fixed+pass → OK`。
`MANUAL` 表示**没检查**，不是没问题——`health.py` 会报覆盖率防止自欺。

### 6.2 已验证有效的证据（不是设想）

| 指标 | 基线（2026-08-30） |
|---|---|
| badcase 自动验证覆盖率 | 67%（6/9；改造前 22%，4 条 fixed 全部未被验证） |
| 修复留存率 | 100%（4/4 fixed 回放通过） |
| 注入故障捕获率 | 1/1——把 A0 的原子写人为回退，回放器判定 REGRESSION 且退出码 1 |
| 跨 seed 确定性 | PYTHONHASHSEED=0/1/2 三轮全过（BC-008 守护） |

注入实验是关键：它证明了**机制真能抓到回归**，而不只是"看起来有机制"。
实验本身也已登记进台账（EXP-003）。

### 6.3 硬约束

- **修复必须带回归测试**：`fixed` 状态的 badcase 若无 `regression_test`，
  测试会直接失败（`tests/test_badcase_replay.py` 守着）。没有测试兜底的修复视为未完成。
- **先登记假设再跑**：台账强制 `propose()` 先写假设与主指标，
  跑完再 `conclude()`。顺序反了就变成给已做的改动编理由。

## 7. 已知隐患：真实业务中会撞上的问题

按"撞上的必然性 × 后果严重度"排序。**以下均为代码核实结果，不是设想。**

### 7.1 数据安全（最高优先级，后果不可逆）

| 隐患 | 核实结果 | 现状 |
|---|---|---|
| KG 非原子写 | `_save()` 原为 `write_text` 直接覆写，写一半崩溃留下半截 JSON | ✅ 已修（A0） |
| 无备份 | 备份只存在于 evals 沙箱脚本，**生产代码路径无备份** | ✅ 已修（A0，保留 `.bak`） |
| 并发写无锁 | 全项目无 `threading.Lock` / `fcntl`；`/api/v1/chat` 是同步 def 会跑在线程池 → 真并发 | ⬜ 待做 |
| L0 无清理 | `EpisodicStore` 只有 `clear()`（清空），无轮转/裁剪/上限。按每天 50 轮算，一年约 1.8 万条 | ⬜ 待做 |

### 7.2 记忆质量（必然会撞上，越晚越难修）

| 隐患 | 说明 | 现状 |
|---|---|---|
| 重复与污染 | 同一件事被写成多条不同表述 → 冲突检测报一堆假冲突。146 节点时已有苗头，千级会爆炸 | 有 `conflict_candidates`，但无自动去重 |
| 时效失效 | 「我在 X 公司」一年后失效，但 supersede 是**人工触发**的，没人会主动改 | 无主动发现机制 |
| L0 噪声累积 | 原文只增不减，检索噪声随时间上升 | 无清理 |

### 7.3 检索与回答（已在代码中确认存在）

| 隐患 | 说明 | 现状 |
|---|---|---|
| 中文整句失配 | 自动注入用整句做关键词匹配，中文不分词 → 命中率≈0 | ⬜ 待做（C3） |
| 无重排 | 检索 top5 里可能只有 1 条相关，LLM 会被不相关的带偏 | 无 rerank |
| 记忆互相矛盾 | 检索到两条相反记忆时，LLM 会随便挑一个 | 无冲突消解策略 |

### 7.4 人的问题（最难，技术解决不了）

| 隐患 | 说明 |
|---|---|
| **审批疲劳** | HITL 的致命伤：待审一多（现已积压 5 条），人会全部点通过 → HITL 形同虚设。需要"批量/自动通过低风险项"的机制 |
| 被记录会改变表达 | 知道自己在被记录，说话会变正式 → 语料质量下降 |
| 提示词注入 | 对外主页上，访客可能诱导它说不该说的话 |
| 期望落差 | 访客可能以为是真人在聊——这正是对外必须显式标注的原因 |
