## 2. LangGraph 到底是什么（澄清一个常见误解）

**误解**：LangGraph 是多 Agent 框架。

**官方定位**（<https://docs.langchain.com/oss/python/langgraph/overview>）：

> "LangGraph is a **low-level orchestration framework and runtime** for building, managing, and deploying **long-running, stateful agents**."

> "LangGraph is focused on the underlying capabilities important for agent orchestration: **durable execution, streaming, human-in-the-loop**, and more."

> "LangGraph provides low-level supporting infrastructure for **any** long-running, stateful workflow or agent."

官方列出的核心能力：**混合确定性与智能体步骤 / 持久化 / 人工介入 / 全面记忆 / 可调试 / 生产部署**——**没有一项是"多 Agent 协调"**。

**多 Agent 在哪一层？** 官方生态描述里写得很清楚：

> "Deep Agents is an agent harness: planning, **subagents**, filesystem tools, and context management **on top of LangGraph**."

即：**多 Agent 是建在 LangGraph 之上的一层，不是 LangGraph 本身。**

### 这对我们意味着什么

**我们用对了。** 我们真正需要的三件事——状态机可回放、短期记忆持久化、写操作中断审批——恰恰是 LangGraph 的核心能力，而且**对单 Agent 完全适用**。

如果它是"多 Agent 专用框架"，那我们才该反思为什么要用它。

## 3. 我们跟多 Agent 有关系吗

### 现状：**单 Agent + 工具**，不是多 Agent

一个 Agent 决策，调 6 个记忆工具，写操作走人工审批。没有 Agent 之间的协商、分工或消息传递。

### 什么时候多 Agent 才真的有用（判据）

避免"为了用而用"，只有满足下列之一才值得拆：

1. **权限需要隔离**：某个角色不该拥有另一角色的工具（如：对话 Agent 不应能直接写库）
2. **需要独立校验**：生成器 + 校验器分离，是降低幻觉最有效的结构之一
3. **上下文可隔离且能并行**：省 token、互不干扰
4. **需要不同的模型或温度**：创意生成 vs 事实校验

### 代价（必须同时考虑）

上下文割裂、协调开销、调试变难、token 成本上升。Anthropic 的公开建议是：**先充分优化单 Agent 的工具使用，不要过早引入多 Agent**。

### 我们项目里的三个天然候选

| 候选 | 价值 | 说明 |
|---|---|---|
| **① 校验 Agent** | ★★★★★ | 对外模式下，一个 Agent 生成回答，另一个**只拿检索到的证据**做 claim 级校验。命中判据 1+2+4（权限隔离、独立校验、低温度）。这是"降低幻觉"最有价值的结构，且我已规划的 verify 节点正好可以升格为独立 Agent |
| **② 记忆管理员 Agent** | ★★★★ | 负责写入、冲突裁决、遗忘提名；对话 Agent 只有检索权，没有写库权。命中判据 1（权限隔离）——**这是把 HITL 从"提示"升级为"架构约束"** |
| **③ 专项模式 Agent**（health_coach） | ★★ | 已有独立 prompt + tools。做成 subgraph 即可，但收益主要是组织清晰度，不是能力 |

**建议**：① 和 ② 有实质收益，放在对外模式之后做；③ 只是整理方式，顺手做。

## 4. 记忆层（现状）

| 层 | 实现 | 状态 |
|---|---|---|
| L0 情景 | 原文轮次 JSONL + 混合检索 | ✅ 已建 |
| L1 语义 | 动力学 KG（146 节点，四桶） | ✅ 已建 |
| 程序记忆 | persona / system prompt | ⚠️ 反刍未接入 LangGraph |
| 遗忘 | `importance × 0.5^(Δt/180)` 衰减 + 归档 | ✅ 已建（参数未标定） |
| 冲突 | supersede 链 + history 版本 | ✅ 代码已建，**真实数据尚未使用** |

**已知缺口**：
- 全库仅 16.2k tokens，规模尚未构成检索压力
- 节点间**边数 = 0**（不是图，是分类桶）；47 条 interactions 运行时取不到
- 打分量纲不统一，参数全部未标定（见「定量」章节）

## 5. 前端形态

### 桌面端（自用 + 演示）
- **对话为中心**，右侧记忆面板（检索到的节点可点开溯源）
- **像素世界默认折叠**——好看但不高效，自用场景不该让它占主界面；演示时展开即亮点
- 顶部 HUD：待审数量 / 模式切换

### 移动端（对外访客）
- 身份卡（**必须显式声明是 AI 代理**）→ 引导问题 chips → 一屏问答 → 带引用角标可溯源 → 转真人口
- 引导清单同时是**幻觉防线里最便宜的一道**：命中率上去，拒答率下来

### 四个已查证的视觉缺陷
1. 两套色系对冲（面板暖棕 `#c8a060` vs 游戏层 GitHub Dark 冷灰 `#0d1117`）
2. `Press Start 2P` 不支持中文，中文回退导致混排断裂
3. HUD 字号 9px / 7px 过小
4. 星露谷原版素材与自制占位素材混用（且公开仓有版权风险）

详见 [`产品形态与前端规划.md`](产品形态与前端规划.md)。

## 6. 预想的操作方式

### 你（自用，桌面端）
1. 打开页面 → 直接提问 → 看到**检索到了哪些记忆节点**（可展开看原文出处）
2. 发现说错了 → 记忆面板里直接改节点 / 标归档 → 走 HITL 生效
3. 每周一次：`memory_maintenance.py forget` 看遗忘提名、`conflicts` 看冲突组 → 批量裁决
4. 心血来潮 → 展开像素世界，点 NPC 进入场景化对话（演示用）

### 访客（移动端，对外）
1. 打开主页 → 看到身份声明 + 引导问题
2. 点一个引导问题（或自由提问）→ 得到带引用角标的回答
3. 想深聊 → 点"转真人"留下联系方式；问到知识外 → 得到"我不确定，建议直接问他"

### 系统（后台，不阻塞对话）
- 写入审批队列（HITL）
- 遗忘提名、冲突检测（background）
- 反刍更新 persona（**待建**）

## 7. 分期

| 阶段 | 内容 | 成本 |
|---|---|---|
| **P0** | 前端静默吞错 + 色系统一 + 字体字号 | 1 天 |
| **P1** | 桌面端改对话为中心，像素世界折叠 | 2–3 天 |
| **P2** | 对外模式三件套（可见性硬隔离 / 只答检索到的 / 转真人 + 引用校验） | 2 天 |
| **P3** | 移动端对外主页 | 3–5 天 |
| **P4** | 多 Agent：校验 Agent + 记忆管理员 Agent | 3 天 |
| **P5** | 定量：打分量纲归一化 + 参数标定 + 不变量断言 | 2 天 |
| **P6** | 素材替换（合规 + 风格统一） | 视素材 |

**依赖关系**：P2 是 P3 的上线前置（对外必须做完可见性隔离和引用校验才能公开）。
P4 依赖 P2（校验 Agent 是 P2 引用校验的升格）。
P5 与前几项无依赖，可并行。

## 8. 定位（不变）

**可信的个人代理——深度在记忆治理，不在工具数量。**

三个"不做"构成差异化：不做微信个人号自动回复（合规）、不冒充本人欺骗面试官（诚信）、不堆通用工具生态（不跟 Hermes 比数量）。
